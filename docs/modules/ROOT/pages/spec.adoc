= Visual App Editor: architecture and roadmap
:page-audience: Developer
:toc:

Visual App Editor is an open-source, offline visual editor for app user interfaces.
It is a framework-neutral core and editing service. Language adapters plug into it (Dart/Flutter today, React and React Native next), and several front ends sit on top: a Flutter desktop app now, IDE plugins later.
This page is the architecture and the roadmap. It states what the editor must do, how the modules fit together, the file formats it reads and writes, and what comes next.
The wire protocol has its own page: xref:protocol.adoc[].

NOTE: The project was called _Widget Bench_ until October 2026. Projects that still have a `widget_bench.sdl` file are read as before; the next save writes `visual_app_editor.sdl`.
Sections marked *Implemented* describe the current code; *Planned* items are on the roadmap.

== Goals

. *Edit real code.* The source of truth is the project's own `.dart` files. There is no proprietary project format that has to be exported.
. *Keep custom code.* Visual edits change only the expressions they touch. Comments, formatting, state classes, helper methods and imports elsewhere in the file survive byte-for-byte.
. *Any widget library.* The toolbox is not hard-coded. It is generated from the public widget constructors (or component props) of whichever packages the project uses.
. *Any framework, one core.* The tree model, catalog, edit operations and device presets are framework-neutral. Each language adds an adapter, not a new editor.
. *Offline.* No account, no cloud service, no telemetry. Everything works from the local Flutter SDK and pub cache.
. *Desktop first.* Windows, Linux and macOS, x64 and arm64 where Flutter supports the host.

=== Non-goals (for now)

* Backend, database or authentication builders.
* Hosting or app-store publishing.
* Editing non-widget logic visually (state management, navigation graphs).

== User interface

[cols="1,3"]
|===
| Area | Behaviour

| Toolbar (top)
| Project name, page picker, Design / Split / Code switch, device size, undo / redo, save, *Run* (live app), open project, About.

| Navigation rail (far left)
| Icons for *Pages*, *Toolbox*, *Tree*, *Theme*, *Toolkits*. Selecting one swaps the left panel.

| Left panel
| Pages list with *New page*; toolbox with search, category groups and drag sources; widget tree with move up / down, wrap-with and delete; theme seed colour, brightness, and *typography* (OSS/retail/mixed preference + catalog face ids stored in `visual_app_editor.sdl`); toolkit list with load / unload and *pub get*.

| Canvas (center)
| The selected page rendered inside a phone, tablet or desktop frame on a dotted backdrop, with zoom. Clicking a widget selects it; the selection is outlined and labelled.

| Properties (right)
| Every constructor parameter of the selected widget, with type, required marker, default value hint and current source expression. Booleans get a switch, colours get swatches; all other values are Dart expressions.

| Code view
| The current file, editable. *Apply* re-parses and refreshes the tree; invalid Dart is refused.

| Status bar
| Last action, edit errors and live-run output.
|===

The editor uses a dark theme. The canvas uses the project's preview theme (seed colour and brightness from `visual_app_editor.sdl`).

== Architecture

*Implemented* unless marked.

=== Modules

[source,text]
----
packages/core       vae_core      framework-neutral model: SDL, tree, catalog, edit ops,
                                  device presets, LanguageAdapter interface, project config
packages/protocol   vae_protocol  JSON-RPC 2.0 framing (Content-Length), method names, peer
packages/service    vae_service   headless editing service: project, documents, undo-free
                                  edit pipeline, toolkit registry, external adapters;
                                  bin/vae_service.dart runs it on stdio
adapters/dart       vae_dart_adapter      Dart/Flutter: analyzer-based introspection,
                                  source edits, bundled toolkit manifests
adapters/react      @devcentr/vae-react-adapter  React + React Native via the TypeScript
                                  compiler API (Node, pnpm); stdio adapter process
apps/desktop        visual_app_editor     Flutter desktop front end + installers
plugins/intellij    visual-app-editor-intellij   IntelliJ / Android Studio front end (Kotlin)
plugins/vscode      visual-app-editor (vsix)     VS Code front end (TypeScript)
----

Dependency rule: `core` depends on nothing but `path`. `protocol` and the adapters depend on `core`. `service` depends on `core`, `protocol` and the bundled Dart adapter. Front ends depend only on `protocol` (plus `core` for the data classes). No front end imports an adapter.

----

 │ plugins/*    │  (stdio or│  project, docs,   │  stdio  ├──────────────┤
 └──────────────┘ in-process)│  toolkits, presets│────────▶│ react (node) │
                            └──────────────────┘         └──────────────┘
----

=== Core model (`vae_core`)

Tree::
`TreeNode` has `type`, a `path` of child indexes from the page root, an optional `slot` (`child`, `body`, `children`, ...), `args` (named or positional source expressions), `children`, source `offset`/`end`, and folded `text`. Dart widgets and JSX elements map onto the same shape: a JSX attribute is a named argument, element children are the `children` slot, and text content is `text`.

Catalog::
`WidgetSpec` (`class`, `toolkit`, `params`, `category`, `doc`, optional `snippet`) and `ToolkitManifest`. A manifest names its `adapter` (default `dart-flutter`).

Edit protocol::
A sealed `EditOp` family: `setArgument`, `removeArgument`, `setPositional`, `setText`, `insertChild`, `removeNode`, `wrapNode`, `moveInList`, `replaceSource`. Every op is JSON-serialisable and is applied by the adapter that owns the file. An adapter that cannot express an op rejects it with `editRejected`, and the source is left unchanged.

Device presets::
`DeviceMode` is one of `phone`, `tablet`, `desktop` or `web`. `DevicePreset` has a logical size, an optional frame and safe areas, and nine built-in presets. Modes are *responsive*: a mode only picks a logical size and chrome. Apps are never edited per mode, and there are no dedicated per-mode layouts. `DevicePresets.modeForWidth` maps an arbitrary width to a mode for breakpoint hints. The desktop toolbar shows a mode switcher (four icons) plus the presets of the active mode.

=== Edit pipeline

. A front end sends `document/edit` with a file, page and op.
. The service routes the file to the adapter that owns its extension (`.dart` to `dart-flutter`, `.tsx`/`.jsx` to `react`).
. The adapter computes a text patch from its own AST, applies it and re-parses. A syntax error rejects the edit.
. The service stores the new source, marks the file dirty, and emits `document/changed` with the new tree.
. `document/save` writes dirty files. Undo / redo live in the front end as whole-file snapshots replayed with `replaceSource`, so every front end can keep its native undo stack.

=== Headless service

`vae_service` speaks JSON-RPC 2.0 framed with `Content-Length` headers, the same framing as LSP, so any LSP client library can talk to it. It runs:

* *out of process*: `dart run packages/service/bin/vae_service.dart` (or a compiled `vae_service` executable) on stdio. IDE plugins will use this.
* *in process*: `connectInProcess()` runs the server in the same isolate but still passes every message through JSON encode/decode, so the in-process path exercises the real wire format. The desktop app uses this by default. Setting `VAE_SERVICE=<command>` makes it spawn an external service instead.

See xref:protocol.adoc[] for the method list.

=== Language adapters

[cols="1,1,3"]
|===
| Adapter | Status | Notes

| `dart-flutter` (`adapters/dart`)
| *Implemented*
| `package:analyzer` (unresolved parse), widget introspection from package sources, all edit ops including const-stripping. Runs inside the service. Bundled manifests are compiled into `bundled_toolkits.dart` (`dart run tool/gen_bundled.dart`) so the service needs no Flutter assets.

| `react` (`adapters/react`)
| *Implemented (first cut)*
| TypeScript compiler API (`typescript` 5.9; the JS API, not the native TS 7 port). Finds components: capitalised function declarations, `const` arrows, `memo`/`forwardRef` wrappers and class `render()`. The root is the returned JSX. All edit ops map onto JSX: props, text children, insert/remove/wrap/reorder elements. Toolkits: a fixed catalog for intrinsic DOM elements (`react-dom`), and real props introspection of any installed package via the type checker on its `.d.ts`, with a built-in React Native core catalog as fallback. Runs as a Node child process (`node adapters/react/dist/cli.js`), registered with `initialize.externalAdapters`.

| `react-native`
| *Implemented, shares `react`*
| Same parser and edits; `toolkits/react-native.sdl` selects the catalog. Preview rendering is planned (see <<preview>>).

| Others
| *Planned*
| The adapter contract (`adapter/pages`, `adapter/applyEdit`, `adapter/loadToolkit` over stdio) is language-agnostic. Candidates: Vue/Svelte single-file components, Angular templates, Ionic (on top of React/Angular/Vue adapters plus an Ionic catalog), legacy Cordova/PhoneGap HTML apps (HTML adapter), Jetpack Compose and SwiftUI (Kotlin/Swift parsers), .NET MAUI XAML.
|===

Adding an adapter means implementing `LanguageAdapter` in Dart, or speaking the three `adapter/*` methods from any language, and shipping SDL manifests with `adapter "<id>"`.

=== Publishing intent

Nothing is published yet. Per the registry choice for each ecosystem, when the APIs settle:

* `vae_core`, `vae_protocol`, `vae_service` and `vae_dart_adapter` go to *pub.dev* (Dart packages; `publish_to: none` until then).
* `@devcentr/vae-react-adapter` goes to *npm* under the `@devcentr` scope (`"private": true` until then).
* The IntelliJ plugin goes to the *JetBrains Marketplace*, and the VS Code extension to the *VS Code Marketplace* and *Open VSX*. Requirements: xref:publishing-ide-plugins.adoc[].
* Desktop installers ship as GitHub Release assets (see <<_packaging_and_delivery>>).

== Toolkit plugins

*Implemented.*
A toolkit is a manifest (see xref:toolkit-manifests.adoc[]) plus the package sources it points at.

Discovery::
Bundled manifests live in `adapters/<adapter>/toolkits/` and are compiled into the adapter. Projects can add or override manifests in `.visual_app_editor/toolkits/`.

Resolution::
Package `lib/` folders come from `.dart_tool/package_config.json`. For the `flutter` package the scanner falls back to `$FLUTTER_ROOT` or the `flutter` executable on `PATH`.

Introspection::
`package:analyzer` parses each file without resolution (`parseString`). This needs no Dart SDK summary, works on unresolved projects, and is fast enough to scan the core, Material and Cupertino libraries (about 500 constructors combined) at project open.
A class is a widget when its superclass chain within the package reaches a known widget base or a manifest `base`.
Each public constructor yields a `WidgetSpec` with ordered parameters: name, declared type (field type for `this.x` and `super.x` parameters when declared), named or positional, required, default value.

Palette::
Entries are grouped by manifest `category`; everything else lands in *Other* (hidden behind the *Common* filter).
The insertion snippet fills required parameters with placeholders based on type (`'label'`, `0`, `false`, `() {}`, `const Text('child')`) and adds `children: []` for multi-child widgets.

*Planned.*

* Resolved introspection (`AnalysisContextCollection`) to follow superclasses across packages, read inherited parameters and expand typedefs.
* Per-toolkit preview adapters so third-party widgets render natively in the in-process preview (see <<preview>>).
* Import management: add the manifest `import` to the file when a widget from a new toolkit is inserted.
* Icons per palette entry from manifest hints.

== Source round-trip

*Implemented.*

Page detection::
Any class whose superclass is `StatelessWidget`, `State<T>` or another `*Widget` and that declares `build`. The page tree root is the expression returned by `build` (expression body or the first `return` outside closures). A `State<T>` page is named after `T`.

Widget recognition::
Without resolution, `Text('a')` parses as a method invocation and `const Text('a')` as an instance creation. Both are accepted, as are `Type.named(...)` and prefixed imports. Known value classes (`EdgeInsets`, `TextStyle`, `BoxDecoration`, `Color`, ...) and types ending in `Style`, `Data` or `Controller` are not treated as widgets; class names from loaded toolkits always are.

Tree::
Named arguments whose value is a widget call become slots (`appBar`, `body`, `child`, `title`, ...). List literals become child lists (`children`, `actions`, `destinations`). Each node has a stable path of child indexes from the page root.

Edits::
[cols="1,3"]
|===
| Operation | Text change

| Set argument | Replace the argument expression, or insert `name: value` before the closing parenthesis, respecting trailing commas and multi-line layout.
| Set positional | Replace or prepend a positional argument.
| Remove argument | Delete `name: value` and its comma.
| Insert child | Append to `children: [...]` (or at an index), or add `child:` when the parent takes a single child and has none.
| Delete | Remove a list element or the named slot that holds the widget.
| Wrap | Replace the node with `Wrapper(extra, child: node)` or `children: [node]`.
| Reorder | Swap two neighbouring list elements.
| Code view | Replace the whole file after a successful parse.
|===

Constness::
Inserting a non-constant expression under a `const` constructor or literal would not compile. Before such an edit the editor removes the enclosing `const` keywords (and turns a `const` local into `final`). Edits whose new text is itself constant (literals, `Colors.x`, enum values) leave `const` alone.

Safety::
Every edit re-parses. Any syntax error rolls the edit back. Undo / redo keep whole-file snapshots.

*Planned.*

* Formatting the edited region with `dart_style`, matching the project's line length.
* Resolved semantic checks (types, missing required arguments) through the analysis server, shown as problems in the properties panel.
* Editing widgets built in helper methods and in other files (follow the call to its declaration).
* Drag to reorder on the canvas and tree.

== Preview

Two complementary approaches exist. Both are part of the design.

=== In-process rendering

*Implemented.*
The page tree from source is interpreted into real Flutter widgets inside the editor.
Literal arguments are evaluated (strings, numbers, booleans, `Colors.*`, `Color(...)`, `EdgeInsets.*`, `BorderRadius.*`, `TextStyle`, `BoxDecoration`, `InputDecoration`, alignment and axis enums, common `Icons.*`).
About sixty common Material, Cupertino and core widgets render natively. Any other widget renders as a labelled frame that still lays out its children, so trees from every toolkit stay visible and selectable.
Callbacks are replaced with no-ops; non-literal values fall back to defaults.

Strengths: instant, works on broken or unresolved projects, selection maps exactly to source nodes.
Limits: no user code runs, so custom widgets, state and data-driven content are approximations.

=== Running the target app

*Implemented (first version).*
*Run* starts `flutter run -d <desktop>` in the project folder. Saving sends `r` (hot reload) to the tool; the VM service URI is captured from its output.

*Planned.*

* Connect to the VM service and use the widget inspector protocol to map the running app's selection back to source locations (`creationLocation`), enabling click-to-select in the real app.
* Embed the running app's frames in the canvas (texture sharing or periodic screenshots via `_flutter.screenshot`) so both previews live in one place.
* A generated preview harness (`.visual_app_editor/preview/main.dart`) that wraps one page in `MaterialApp` with mock data, so a single page can run without the app's navigation.

[[device-preview]]
=== Live device simulation with `device_preview`

*Planned.*
For the running app, device modes come from the `device_preview` package (3.x). It is a custom `WidgetsBinding` that simulates screen size, pixel ratio, safe areas, orientation, keyboard, locale, brightness, text scale, accessibility flags and target platform. It has no in-app UI and is driven from Dart. It is inactive in release builds.

. The generated preview harness calls `DevicePreview.enable()` before `runApp`. The user's own `main.dart` is not modified. `device_preview` is added as a `dev_dependency` only on the user's request.
. The harness registers a VM service extension (`ext.vae.device`) that takes a `DevicePreset` JSON and calls `DevicePreview.controller.update(...)`/`setOrientation(...)`.
. When the user switches mode or preset in the toolbar, the front end calls the extension, and the running app re-lays out with no rebuild or restart.
. The in-process canvas keeps using `vae_core` presets, so the static and live previews agree on sizes and safe areas.

React Native's live preview is planned on the same model: a Metro dev server plus a preview harness. React for the web uses a sized iframe with the same presets.

== File formats

All editor configuration uses SDL (https://sdlang.org[Simple Declarative Language]).

=== Project settings: `visual_app_editor.sdl`

Lives in the project root. Safe to commit.

[source,sdl]
----
project "sample_app" {
	toolkits "widgets" "material" "cupertino"   // manifest ids to load
	device "pixel-8"                             // a DevicePreset id; mode follows
	theme seed="#4B8BFF" brightness="light"      // preview theme only
}
----

=== Toolkit manifests: `toolkits/*.sdl`

See xref:toolkit-manifests.adoc[].

=== Dart sources

Ordinary Flutter code. Visual App Editor adds nothing to it: no markers, no generated regions.

[cols="1,1,2"]
|===
| Platform | Architectures | Artifact

| Windows | x64, arm64 | Inno Setup installer (`apps/desktop/packaging/windows/build-installer.ps1`)
| Linux | x64, arm64 | AppImage and `.deb` (`apps/desktop/packaging/linux/build-packages.sh`)

The version shown in About and `--version` comes from `--dart-define=VAE_VERSION` / `VAE_BUILD`, stamped by CI.
